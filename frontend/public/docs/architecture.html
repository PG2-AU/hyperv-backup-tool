01 Zweck & Anforderungen

Klassische Agenten-Backups sind auf virtualisierten Windows-Failover-Clustern teuer und langsam. Das Tool sichert stattdessen auf Storage-Ebene: Hyper-V liefert die Anwendungskonsistenz (Checkpoints), NetApp ONTAP liefert die eigentlichen, platzsparenden Snapshots. Daraus ergeben sich die zentralen Anforderungen:

01
Storage-basierte Sicherung ohne Agenten Hyper-V-Checkpoint (crash- oder anwendungskonsistent) + NetApp-Snapshot pro betroffenem Volume, gesteuert über Policies mit Zeitplan und Retention.
02
Zwei Schutz-Granularitäten Eine Schutzgruppe kann einzelne VMs oder ganze Cluster Shared Volumes (CSV) umfassen — je nachdem, ob VMs individuell oder blockweise gesichert werden sollen.
03
Off-Site-Kopie via SnapMirror, automatisch genutzt Nach jedem Backup optional ein SnapMirror-Update anstoßen. Beim Restore wird immer zuerst das Primärsystem geprüft — erst wenn der Snapshot dort fehlt, greift automatisch die Replik auf dem SnapMirror-Ziel, ganz ohne manuelle Auswahl.
04
Mehrere Wiederherstellungswege Vom einzelnen Datei-Restore bis zur kompletten Neuerstellung einer gelöschten VM oder einem Side-by-side-Klon zu Testzwecken — siehe Abschnitt 06.
05
Rollenbasierte Zugriffskontrolle Eigene Benutzerverwaltung mit Rechte-Rollen, optional angebunden an Active Directory — das Tool greift auf produktive Infrastruktur zu.
06
Geringer Betriebsaufwand Ein internes Werkzeug für ein kleines Team, kein Multi-Tenant-SaaS — entsprechend schlank gehalten: eine Instanz, ein Container, Selbst-Update statt CI/CD-Pipeline.

03 Die Schichten

Vier Verantwortungsbereiche, sauber getrennt:

Client

Oberfläche

Dashboard, Inventar, Schutzgruppen, Job-Verlauf und die Restore-Wizards. Reine Anzeige- und Formularlogik, kein eigener Zustand über einen Request hinaus.

React · TypeScript · Mantine UI · TanStack Query

Kern

API & Domänenlogik

Policies, Schutzgruppen, Zeitpläne, Backup-/Restore-Läufe als Datenbank-Modelle; jeder mehrstufige Vorgang schreibt seinen Fortschritt Schritt für Schritt mit, damit er live verfolgt und im Nachhinein geprüft werden kann.

FastAPI · Pydantic · SQLAlchemy 2.0 · SQLite

Integration

Hyper-V-Anbindung

PowerShell-Remoting gegen den Cluster-Zugriffspunkt und einzelne Knoten: Inventar auslesen, Checkpoints setzen, VMs anlegen/konfigurieren, Cluster-Rollen registrieren.

pywinrm · NTLM / CredSSP

Integration

NetApp-Anbindung

ONTAP-REST-API für Snapshots, LUN-/Volume-Klone, SnapMirror-Beziehungen und -Policies. Ein DP-Volume (SnapMirror-Ziel) kann keine LUN direkt klonen — dafür wird das gesamte Volume per FlexClone gespiegelt.

netapp_ontap SDK

Infrastruktur

Restore-Proxy-Host

Ein schlanker Windows-Host mit nativem iSCSI-Initiator, den das Backend per WinRM fernsteuert. Hier werden Klone gemountet, VHDX durchsucht und Dateien kopiert — ohne dass ein Hyper-V-Produktivknoten selbst iSCSI sprechen muss.

WinRM · iSCSI · SMB

04 Kernkonzepte

Das Vokabular, mit dem sich der Rest der Anwendung erklärt:

Policy
Bündelt Konsistenz-Typ (crash/app), Zeitplan, Retention und optional eine SnapMirror-Regel. Wiederverwendbar über mehrere Schutzgruppen.
Schutzgruppe
Eine Menge von VMs oder CSVs, die gemeinsam nach derselben Policy gesichert werden.
Backup-Lauf
Eine Ausführung einer Policy: pro betroffenem NetApp-Volume ein Snapshot, pro Schritt (Checkpoint, Snapshot, SnapMirror-Update) ein protokollierter Eintrag.
Primär / Sekundär
Ein Snapshot gilt als „primär“, solange er auf dem Quellsystem existiert. Wird er dort entfernt, aber liegt noch auf einem SnapMirror-Ziel vor, gilt er als „sekundär“ — weiterhin restorebar, nur die Quelle wechselt automatisch.
Restore-Infrastruktur
Pro Ziel-SVM hinterlegte iSCSI-/Igroup-Konfiguration, ohne die kein Restore für diese SVM technisch möglich ist.

05 Ablauf: Backup

Ausgelöst manuell oder per Zeitplan, für eine ganze Schutzgruppe:

Checkpoint je VM. Hyper-V erstellt einen Produktions- (anwendungskonsistenten) oder Standard-Checkpoint, abhängig von der Policy.

Snapshot je Volume. NetApp erstellt für jedes betroffene Volume einen benannten Snapshot — der eigentliche, platzsparende Wiederherstellungspunkt.

Checkpoint entfernen. Der Hyper-V-Checkpoint wird sofort wieder gelöscht; er diente nur der Konsistenz während des Snapshots.

SnapMirror-Update (optional). Ist die Policy dafür konfiguriert, wird die Replikation zum Ziel-System angestoßen — asynchron, blockiert den Lauf nicht.

VM-Konfiguration sichern. CPU, RAM, Netzwerkadapter und die VHD-zu-LUN-Zuordnung werden zum Zeitpunkt der Sicherung mit gespeichert — Grundlage für eine spätere komplette Neuerstellung.

Jeder dieser Schritte landet einzeln im Job-Verlauf — inklusive Klartext-Fehlermeldung, falls er fehlschlägt.

06 Ablauf: Restore

Der interessante Teil ist die Quellenwahl: die Anwendung entscheidet selbst, ob vom Primär- oder Sekundärsystem restored wird — nie der Nutzer.

Automatischer Primär-vor-Sekundär-Fallback, keine manuelle Quellenauswahl

Technischer Hintergrund: Ein SnapMirror-Ziel ist ein schreibgeschütztes DP-Volume — ein direkter LUN-Klon daraus wird von ONTAP abgelehnt. Der Restore-Pfad weicht in diesem Fall auf einen Klon des gesamten Volumes aus, in dem die LUN bereits enthalten ist.

07 Restore-Varianten

Ab dem geklonten/gemounteten Snapshot verzweigt der Restore in fünf Varianten:

VarianteWirkungBetrifft Original
AnhängenVHDX als Zusatzdisk an die laufende VM hängen, kein Downtime.unverändert
ErsetzenLaufende VHDX kurz stoppen, austauschen, alte Datei löschen.wird ersetzt
Datei-RestoreVHDX schreibgeschützt mounten, im Dateibaum durchsuchen, gezielt Dateien kopieren.unverändert
VM neu erstellenKomplette Neuerstellung einer gelöschten VM unter demselben Namen.existiert nicht mehr
Side-by-sideKomplette VM unter neuem Namen zusätzlich anlegen — eigener Speicherort, Netzwerk optional getrennt.läuft parallel weiter

08 Betrieb & Deployment

Bewusst klein gehalten, passend zum Nutzerkreis:

Ein Container. Backend, Frontend-Build und SQLite-Datenbank laufen zusammen in einem rootless Podman-Container.

Selbst-Update statt Pipeline. Ein Supervisor-Prozess zieht periodisch git pull, installiert Abhängigkeiten bei Bedarf nach und startet neu — kein separates CI/CD-System nötig.

Additive Schema-Migration. Neue Datenbankspalten werden beim Start automatisch ergänzt, ohne bestehende Daten anzufassen.

Hintergrund-Jobs im selben Prozess. Discovery, geplante Backups, Retention und Aufräumarbeiten laufen als eingebettete Scheduler-Jobs — kein separater Worker.
